    Clean-room provenance

    Liquid LSD may be sold, so every algorithm that comes from someone else's work needs a recorded source and method. This file is the ledger. Add a row before a new algorithm ships, not after. It records what the repository itself shows; items only the owner can confirm are marked To confirm and should be settled (and ideally attested in writing) before a commercial release.

    The rules

    • Allowed sources: a published paper, our own derivation, textbook mathematics, and black-box observation of a running program (below).
    • Not allowed: reading, copying, decompiling, disassembling or recalling-and-copying another program's source code, including GPL/LGPL code. Shader, OpenCL or script files that an app ships as plain text count as source. A forum post or wiki page that quotes an app's code counts too.
    • Counts are fine. Statistics about which variations flames use (flameStats) copy no genome and no code. Only the tallies are kept or published.
    • Separate the roles where a formula is not in a paper: whoever observes the other program never writes our code, and whoever writes our code sees only the written observations.

The sweep also showed 50 variations matching outright, 13 more matching as a set (dots decoded to the wrong input where outputs collide), and 11 flagged with only a handful of mismatches each; those are boundary points (rectangles at y = 0), far points where a dot's tiny size is amplified (swirl), and branch cuts (log at the negative x axis), not formula differences. waves and modulus returned no data (they depend on the transform's own coefficients); the probe now takes a known translation (--translate), and with it rings, waves, modulus (as a set) and popcorn match, fan was corrected.

    The assistant that implements may have seen flame-program formulas in its general training. The rule is therefore that it derives each formula from the observed table alone and lets the table decide; a formula that does not fit the table is wrong whatever it remembers.

    Black-box protocol for new variations

    1. Pick the variation from the statistics, not from a source. Name, rank and parameter names are facts about files. tools/blackbox/make_probes.py builds the probe flames; see its README.
    2. Observer (a person, or an agent that writes no implementation code): run the other program as a user would. Build a flame with one xform, identity pre-affine, weight 1, only the variation under study, and (if the program allows) a final xform of identity. Record only what the program shows or exports by design:
    3. rendered images at fixed settings, and any point or parameter values it shows or saves;
    4. for deterministic variations, where chosen input points land (a grid, the axes, a ring, near-origin points); a handful of exact pairs from a fine sweep is the goal;
    5. for random ones, the distribution of the output (moments, a histogram) over many samples;
    6. the parameters it exposes, with their defaults and the range its UI allows. Write these into a spec file shaped like .planning/flame-variations-spec.md (inputs, outputs, tolerances). No formulas, no code, no screenshots of source.
    7. Implementer reads only that file and the paper, derives a formula that reproduces the table, implements it, and adds the pairs as unit tests. If two formulas fit, the observer adds probe points to separate them.
    8. Check by image: render the same flame in our engine and in the program and compare. Differences go back to the observer as new probes, never as "the original does X".
    9. Log it: add a ledger row (variation, date, observer, implementer, spec file, tests). Anything the observer or implementer was unsure the rules allowed is recorded and the item is dropped or redone.

    The reverse-engineering tools (decompilers, memory inspection) are not part of this protocol.
